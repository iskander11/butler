# Дворецкий: руководство пользователя

## Для чего нужен Butler

Butler управляет сетевым доступом к сервисам на Linux-сервере. Например,
на сервере могут работать файловое хранилище, сайт, карты и другие приложения.
Панель определяет, кто сможет подключиться к их портам.

Butler не запускает и не останавливает эти приложения. Если приложение выключено,
добавление его порта в список не запустит его. Если приложение включено, закрытый
доступ не означает, что оно перестало работать внутри сервера.

## Три правила доступа

1. **Сервиса нет в списке:** внешним клиентам доступ должен быть закрыт.
2. **Сервис добавлен, активный белый список пуст:** доступ разрешён всем клиентам,
   которые могут добраться до сервера по сети.
3. **Сервис добавлен, в белом списке есть активные адреса:** доступ разрешён только
   этим адресам и подсетям. Остальные клиенты доступа не получают.

Белый список общий для добавленных сервисов. Он не открывает отсутствующий в
списке сервис. Выключенные записи белого списка не участвуют в правилах:
если все записи выключены, список для фильтрации считается пустым.

SSH на TCP-порту **22** и веб-панель Butler (обычно TCP **5050**) — исключения:
они сохраняют доступ независимо от белого списка. Это нужно для управления сервером.
Нестандартный порт SSH автоматически не определяется.

## Сохранение и применение — разные действия

Добавление, редактирование, включение, выключение или удаление записи сначала
меняет данные в панели. Сетевой доступ остаётся таким, каким был после предыдущего
успешного применения.

Чтобы изменения начали действовать:

1. Подготовьте список сервисов и белый список.
2. Откройте страницу правил.
3. Нажмите **«Применить правила»** и дождитесь ответа.
4. При успехе появится **«Правила применены.»**

Не закрывайте страницу, пока операция выполняется. Повторное применение из
другой вкладки одновременно с первым отклоняется. Если появилось сообщение об
ошибке, считать настройку завершённой нельзя: часть команд могла уже выполниться.
Сохраните текст ошибки для администратора.

## Как добавить сервис

1. Узнайте порт, по которому клиент подключается к серверу.
2. Откройте раздел сервисов и укажите понятное название.
3. Укажите порт или несколько портов через запятую. Поддерживаются диапазоны,
   например `8000-8005`.
4. Выберите протокол: TCP, UDP или оба. Он должен соответствовать приложению.
5. Сохраните запись и примените правила.

Для Docker указывается **внешний порт сервера**. Если публикация выглядит как
`8020:80`, в Butler нужен `8020`, потому что пользователь открывает
`http://адрес-сервера:8020`. Внутренний `80` определяется при применении.

Если одно приложение использует несколько портов, добавьте все необходимые.
Название сервиса служит подписью: фильтрация выполняется по портам и протоколам,
а не по имени приложения или контейнера.

## Как заполнить белый список

Добавьте IP-адрес клиента, сохраните активную запись и примените правила.
Можно указать подсеть, например `192.0.2.0/24`: тогда разрешение распространяется
на все адреса этой подсети. Для одного устройства используйте отдельный IP.

Нужен адрес, **который видит сервер**. При VPN он может отличаться от адреса
домашней сети. Если несколько устройств выходят через один NAT или прокси,
сервер может видеть их как один адрес. По такому адресу Butler не сможет
различить эти устройства.

Удаление или выключение последней активной записи после применения делает
добавленные сервисы общедоступными. Пустой белый список не означает «запретить всем».
Для закрытия конкретного сервиса удалите его порт из списка сервисов и примените правила.

## Что происходит при применении

Butler защищает управляющие порты, устанавливает политику запрета остальных
входящих подключений и заменяет свои правила правилами из текущих списков.
Одинаковые разрешения для нескольких портов объединяются, чтобы сократить число команд.

Для обычных процессов используются правила входящего трафика UFW. Для
опубликованных Docker-портов дополнительно проверяются контейнеры и создаются
правила пересылаемого трафика к их внутренним адресам и портам. Настройка
Docker выполняется встроенной адаптированной копией `ufw-docker`.

Старые входящие соединения тоже должны подчиняться новому запрету. Ответы на
соединения, которые сам сервер начал наружу, сохраняют разрешённый путь.
Готовая страница в браузере при этом не исчезнет: уже загруженные данные остаются
на экране. Проверять нужно новый запрос, обновление данных или новое подключение.

На проверенном сервере повторное применение занимало примерно **4–5 секунд**.
Это измерение конкретной конфигурации, а не обещание одинакового времени для
любого количества правил и любой машины.

## Почему раньше сервисы оставались доступны — простыми словами

Представьте дом с охранником у главной двери. Обычные приложения входят через
эту дверь. У контейнеров Docker есть другой проход. Проверять только главную
дверь недостаточно: посетитель может попасть внутрь через другой проход.

В Linux это два разных маршрута пакетов: к процессу на самом сервере и через
сервер в контейнер. Docker перенаправляет опубликованный порт во внутреннюю
сеть контейнера. Обычного `ufw allow/deny` на входящем порту сервера для этого
пути недостаточно — нужны правила пересылки и цепочка `DOCKER-USER`.

Дополнительно нашлись ещё две ошибки:

1. **Охранник не успевал получить весь новый список.** Веб-сервер завершал
   обработчик после 30 секунд. Часть правил успевала измениться, а правила
   Docker — ещё нет. Получалась незавершённая настройка.
2. **Старому посетителю больше не проверяли пропуск.** Ранее открытые соединения
   пропускались как уже установленные до проверки новых ограничений.
   Простое удаление записи о соединении оказалось ненадёжным: сетевой стек
   мог заново распознать продолжающееся TCP-соединение в обратном направлении.

Поэтому исправление состоит не в особом запрете одного порта. Проверка охватывает
оба пути трафика и уже существующие входящие соединения. Убраны лишние команды,
увеличен тайм-аут обработчика и запрещено одновременное применение из двух вкладок.

В разобранном случае **8020 работал через Docker**, а **8888 обслуживал обычный
процесс на сервере**. Одинаковое внешнее проявление имело разные причины.

## Границы проверки

Живые проверки выполнялись для IPv4, обычного TCP-сервиса и Docker bridge с
опубликованным TCP-портом. Проверены пустой список, разрешённый и запрещённый
клиент, удаление сервиса и старые HTTP keep-alive соединения. Это не сертификация
всех вариантов Docker, IPv6, UDP, прокси и сетевых маршрутов.

Другие средства управления фаерволом могут менять те же правила. После изменения
публикации портов или пересоздания контейнеров примените правила заново и проверьте
доступ: адрес контейнера может измениться. Сценарии с несколькими внешними портами,
ведущими на один внутренний порт контейнера, требуют отдельной проверки.

Пошаговая пользовательская проверка находится в [TESTING.md](TESTING.md).

# Проверка Дворецкого пользователем

## Перед началом

Проводите проверки на тестовом сервере или в согласованное время: они намеренно
меняют доступ к сервисам. Сохраните исходные списки, чтобы вернуть настройки.
Оставьте открытой SSH-сессию; для проверки управления также открывайте новую.

Нужны:

- Адрес сервера и доступ к панели Butler.
- Два устройства A и B, которые сервер видит с разными IP.
- Два работающих тестовых сервиса: обычный процесс и контейнер Docker.
  Далее для примера используются TCP-порты 8888 и 8020.
- Знание протокола и внешнего порта каждого сервиса. Для публикации Docker
  `8020:80` в панели указывается 8020.

Устройства за одним NAT могут выглядеть для сервера одинаково. Если это ваш
случай, используйте разные маршруты или VPN-адреса и уточните у администратора,
какие адреса видны серверу. Проверка из браузера самого сервера или через
SSH-туннель не заменяет проверку с внешнего клиента.

Для каждого шага запишите время, адрес устройства, порт, действие и результат.
Если результат отличается от ожидаемого, сохраните текст ошибки и остановите
проверку до выяснения причины.

## Как проверять доступ

Откройте сервис в браузере и выполните новый запрос. Уже нарисованная страница
может остаться на экране после запрета. Отключите кэш в инструментах разработчика
или используйте команду:

```bash
curl --noproxy '*' --connect-timeout 3 --max-time 5 -I http://SERVER:8020/
curl --noproxy '*' --connect-timeout 3 --max-time 5 -I http://SERVER:8888/
```

Замените SERVER адресом сервера; в Windows используйте `curl.exe`.
Для HTTPS укажите правильную схему. Ответ HTTP, в том числе 301, 302, 401,
404 или 405, означает, что сетевой доступ есть. Ошибка авторизации приложения
не доказывает блокировку фаерволом. Тайм-аут может означать запрет, но также
неработающий сервис: сначала убедитесь, что он действительно запущен.

## 1. Сервис отсутствует в списке

1. Удалите тестовые порты из всех записей сервисов, включая списки и диапазоны.
2. Убедитесь, что активных записей белого списка нет.
3. Нажмите «Применить правила» и дождитесь «Правила применены.».
4. С устройств A и B проверьте оба сервиса.

**Ожидается:** оба сервиса недоступны с обоих устройств. SSH и панель доступны.

## 2. Сохранение без применения

1. Добавьте оба тестовых сервиса и сохраните записи.
2. Не нажимайте «Применить правила».
3. Повторите проверку с A и B.

**Ожидается:** доступ всё ещё закрыт, как на предыдущем шаге.

## 3. Пустой белый список

1. Примените правила с добавленными сервисами и пустым активным белым списком.
2. Проверьте оба сервиса с A и B.

**Ожидается:** оба сервиса доступны обоим устройствам.

## 4. Только одно разрешённое устройство

1. Добавьте в белый список только IP устройства A и оставьте запись активной.
2. До применения проверьте B: доступ пока должен оставаться открытым.
3. Примените правила.
4. Проверьте оба сервиса с A и B новыми запросами.

**Ожидается:** A получает доступ к обоим сервисам, B — ни к одному.
Наличие разрешённого IP не открывает другие порты, отсутствующие в сервисах.

## 5. Уже открытое соединение

1. Вернитесь к пустому активному белому списку и примените правила.
2. С B откройте оба сервиса. По возможности запустите поток данных,
   периодическое обновление или WebSocket, чтобы соединение сохранялось.
3. Разрешите только A и примените правила.
4. На B запросите новые данные в уже открытом соединении и отдельно создайте новое.

**Ожидается:** B не получает новые данные ни по старому, ни по новому соединению.
Ранее загруженная страница или буфер видео могут оставаться видимыми.
Если приложение не держит соединение открытым, этот шаг проверяет только новые
соединения; проверку HTTP keep-alive должен дополнительно выполнить администратор.

## 6. Несколько адресов и выключенные записи

1. При разрешённом A добавьте активный IP устройства B и примените правила.
2. Проверьте оба устройства: доступ должен быть у обоих.
3. Выключите запись B, оставив A активным, и примените правила.
4. Проверьте снова: доступ должен остаться только у A.
5. Выключите также A и примените правила.

**Ожидается:** активный белый список теперь пуст, оба добавленных сервиса доступны
всем. Наличие выключенных строк не включает ограничения.

## 7. Удаление последнего разрешённого IP

1. Оставьте только одну активную запись A и примените правила.
2. Удалите её, затем примените правила.
3. Проверьте A и B.

**Ожидается:** добавленные сервисы доступны обоим устройствам.

## 8. Удаление сервиса

1. При открытом доступе удалите 8020 из всех записей сервисов.
2. До применения он должен продолжать открываться.
3. Примените правила и проверьте 8020 и 8888.
4. Повторите проверку, удалив 8888, а затем применив правила.

**Ожидается:** удалённый порт закрыт, оставшийся добавленный порт работает
согласно белому списку. После удаления обоих закрыты оба. По возможности
проверьте также соединения, открытые до удаления.

## 9. Несколько портов и протокол

1. Добавьте запись с несколькими тестовыми портами через запятую, примените правила.
2. Проверьте каждый порт отдельно, затем один действительно работающий порт,
   который в запись не входит.
3. Если используются диапазоны, проверьте начало, конец и порт вне диапазона.
4. Для UDP используйте клиент соответствующего приложения. Браузер и TCP-проверка
   не подтверждают работу UDP.

**Ожидается:** разрешение распространяется только на указанные порты и протоколы,
с учётом белого списка. Не используйте порт без запущенного сервиса как единственное
доказательство правильной блокировки.

## 10. Повторное применение и управление

1. Дважды последовательно примените неизменённые правила.
2. Каждый раз дождитесь сообщения об успехе и измерьте время.
3. Убедитесь, что результат доступа не меняется.
4. Откройте новое SSH-подключение на 22 и новую вкладку панели Butler.
5. В тестовой среде попробуйте применить правила из второй вкладки,
   пока первая операция ещё выполняется.

**Ожидается:** правила не дублируются, SSH и панель доступны, одновременное
применение отклоняется понятным сообщением. На проверенной конфигурации
последовательное применение занимало около 4–5 секунд; для другой машины
фиксированное время не гарантируется. Успешное сообщение не содержит пути
к сгенерированному файлу.

## 11. Проверка после перезапуска

В согласованное время попросите администратора перезапустить Butler.
Проверьте сохранность списков и доступа. Сам перезапуск панели не должен
самовольно применять ещё не применённые изменения списков.

После пересоздания Docker-контейнера проверьте публикацию портов, заново
примените правила и повторите шаги 3–5. Перезагрузку всего сервера и Docker
проводите только в согласованное окно обслуживания.

## 12. Завершение

1. Восстановите исходные сервисы и белый список.
2. Примените правила.
3. Проверьте нужные рабочие сервисы, SSH и панель.
4. Передайте результат: какие шаги пройдены, откуда выполнялась проверка,
   какие IP видел сервер, время применения и точный текст ошибок, если они были.

Не передавайте пароли, токены и файл butler.env вместе с отчётом.

## Администратору: автоматические тесты

Запускать в отдельном каталоге исходников на Linux с Python 3.11:

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt pytest==8.3.5
.venv/bin/python -m pytest -q
```

Тесты используют временные базы и подменяют системные команды, чтобы не менять
фаервол тестовой машины. На подготовленном обновлении пройдено 86 тестов.
Автотесты не заменяют сетевые проверки с внешних устройств.
